# Переход с Supabase на собственный бэкенд на Laravel

Статус: **отложено** · 2026-11-02. Пока остаёмся на Supabase, заморозки схемы нет.
План хранится на случай, если переход понадобится. При вайб-кодинге хостинг тогда стоит
пересмотреть в пользу managed вместо VPS.

Решения на момент написания: Laravel и Postgres, VPS в Германии, схема БД заморожена на время
перехода, вход через Apple добавляем в фазе auth.

## 1. Главное

- **Сейчас удачный момент.** Продакшена нет. На staging 4 пользователя, 2 мастера,
  225 записей и 14 МБ данных. Позже такой переход обойдётся в разы дороже.
- **Причина медленных запросов не в Supabase, а в географии и числе запросов к базе.**
  Замер ниже показывает 2,5–4 с. Laravel, поставленный не рядом с базой, будет таким же
  медленным.
- **Зависимость от Supabase неглубокая.** Realtime и Edge Functions не используются,
  в Storage лежит 3 файла, cron-задача одна. Основная работа: auth, 18 функций в базе
  и замена RLS.
- **Самый большой новый риск: утечка данных между мастерами.** RLS больше не страхует,
  поэтому изоляция проверяется обязательным тестом на каждый эндпоинт.
- **Срок: около 7–9 недель на одного человека.** Оценка грубая.

## 2. Текущее состояние

### Что используется

| Часть Supabase | Факт | Что будет |
| --- | --- | --- |
| Auth | email-код и Google, 4 пользователя, паролей нет | Sanctum, свой email-код, Google, Apple |
| PostgREST из мобилки | 57 функций в 11 файлах `entities/*/api` | REST API `/v1/app/*` |
| Функции в базе | 18 штук; крупнейшая `create_appointment_from_booking`, около 11,8 КБ | PHP-классы; аналитика остаётся на SQL |
| RLS | 41 `CREATE POLICY` в миграциях | Policies, tenant scope, тесты изоляции |
| Storage | бакеты `avatars`, `master-media`, 3 файла | Cloudflare R2 |
| pg_cron | 1 задача (`expire-stale-pending-appointments`) | Laravel Scheduler |
| Realtime, Edge Functions | не используются | не нужны |
| Сервер Nuxt | 15 маршрутов `server/api` на service role | переезжают в Laravel, кроме `/api/country` |

Выгодно то, что в мобилке с Supabase работают только файлы `entities/*/api` и
`shared/api/supabase.ts`, это проверяет ESLint. Экраны почти не изменятся.

9 запросов к staging с этой машины, 2026-11-02. Холодные старты не исключались, замер
ориентировочный.

| Запрос | Время до первого байта |
| --- | --- |
| `GET /api/master/karinami/availability` | 2,5–4,0 с |
| `GET /api/master/karinami` | 2,1–2,3 с |
| Supabase напрямую (`auth/v1/health`) | 0,22–0,33 с |

`x-vercel-id: fra1::iad1::…` показывает, что функция работает в США, а база стоит в

это съедает большую часть времени, но разбивку по шагам я не измерял.

## 3. Целевая архитектура

```text
Мобилка ──────────────────────────────┐
                                      ▼
Браузер → Nuxt (Cloudflare) → proxy → Cloudflare → Laravel + Octane (Германия)
                                                     ├─ Postgres 17 (частная сеть)
                                                     ├─ Valkey (кеш, очереди, лимиты)
                                                     ├─ Horizon (очереди), Scheduler
                                                     └─ R2 (файлы) · WhatsApp/Telegram · Email
```

### Стек

| Слой | Выбор | Почему |
| --- | --- | --- |
| Фреймворк | Laravel 13, PHP 8.4 | Laravel 14, по данным Laravel News, потребует 8.4, поэтому обновление будет проще |
| Сервер приложения | Octane + FrankenPHP | приложение не загружается заново на каждый запрос |
| База | PostgreSQL 17 | та же мажорная версия, что на staging |
| Кеш и очереди | Valkey (совместим с Redis) + Horizon | один сервис и наблюдаемые очереди |
| Токены | Sanctum, непрозрачные токены на устройство | можно отозвать сразу; refresh-логика не нужна |
| Контракт API | Scramble → OpenAPI → `openapi-typescript` | типы для Nuxt и мобилки вместо `database.types.ts` |
| Качество | Pest, Larastan, Pint | тесты и статический анализ в CI |
| Наблюдаемость | Sentry (уже в мобилке), Pulse, `pg_stat_statements` | ошибки и медленные запросы |
| Работа с AI-агентом | Laravel Boost | контекст проекта и документация для агентов |

### Структура кода

Код живёт в `apps/api` и делится по доменам:

```text
app/Domain/{Auth,Masters,Scheduling,Booking,Clients,Appointments,Sales,Analytics,Messaging,Media}
  Actions/   одна бизнес-операция в транзакции
  Models/    Eloquent
  Queries/   сложное чтение на SQL
app/Http/{Controllers,Requests,Resources}   тонкий HTTP-слой
routes/api.php   /v1/public/*  и  /v1/app/* (auth:sanctum)
```

Правила:

- Любая запись идёт только через Action. На этом держатся блокировки и сброс кеша.
- Поля API остаются в `snake_case` и повторяют нынешние строки таблиц. Модели мобилки
  почти не меняются.
- Логика занятости и слотов есть только в API. Мобилка оставляет у себя лишь отображение.

### Сайт: прокси вместо прямых вызовов

Браузер продолжает ходить на тот же адрес `/api/*`, а Nuxt проксирует в Laravel через
`routeRules`.

- Не нужны CORS и междоменные cookie: `seene_holder` и токен устройства остаются на домене сайта.
- Staging может остаться на домене `vercel.app`.
- Клиентский код почти не меняется, и переносить можно по одному маршруту.

Что нельзя забыть:

- Настоящий IP клиента надо передавать с секретом прокси, иначе лимиты сработают на всех сразу.
- Эти cookie исключаем из шифрования Laravel и хешируем тем же алгоритмом, что сейчас.
- Функцию Nuxt на Vercel переносим в `fra1`, иначе останется крюк через США.

## 4. Поиск слотов

Таблицу заранее посчитанных слотов не делаем. Для соло-мастера занятость за весь горизонт
это максимум сотни строк: расчёт на лету дешевле и не даёт устаревших данных.

### Алгоритм

Чистый класс `SlotEngine` без обращений к базе используют **все**: `availability`,
`nearest`, `hold`, создание брони и перенос. Правила не смогут разойтись.

1. Контекст: расписание, часовой пояс, настройки.
2. **Один** SQL-запрос на всю занятость диапазона (`UNION ALL` записей, личного времени и
   чужих hold), включая интервалы, начатые раньше диапазона.
3. Для каждого дня границы считаются через `DateTimeImmutable` в поясе мастера, что
   закрывает перевод часов. Дальше идёт работа с целыми числами.
4. Вычитание занятого из рабочего времени одним проходом по отсортированным спискам, O(n + m).
5. Генерация слотов по сетке, затем фильтры: минимальное уведомление, отпуск, горизонт.
6. `nearest` останавливается на первом найденном слоте и не считает весь горизонт.

### Единые правила вместо сегодняшних расхождений

- **Буфер** идёт после визита. Новый визит вместе со своим буфером должен закончиться до начала следующего.
- **Сетка** отсчитывается от начала каждого рабочего отрезка. После перерыва это его конец: так
  сайт работает уже сейчас, и такие слоты больше не будут отклоняться.
- **Активные статусы** перечислены в одном месте.
- **Проверка брони** вызывает тот же движок и смотрит, есть ли этот слот в его результате.

### Защита от двойной брони

Два уровня:

1. **Блокировка на мастера** (`pg_advisory_xact_lock`) в транзакции. Механизм уже работает.
   Через него теперь идут и записи, которые создаёт мастер.
2. **Страховка на уровне базы:** `EXCLUDE USING gist` по мастеру и интервалу.

```sql
-- нужно расширение btree_gist
EXCLUDE USING gist (user_id WITH =, tstzrange(start_at, end_at) WITH &&)
  WHERE (status IN ('pending', 'confirmed') AND NOT allow_overlap);
```

В приложении мастер видит предупреждение о пересечении, а на staging уже есть одна такая
пара записей. Значит, осознанное пересечение нужно разрешить флагом `allow_overlap`.

**Уточнить в фазе 1:** подтвердить, что мастер действительно может сохранить запись поверх
другой. Если нет, флаг убираем и проверка становится строже.

### Индексы

```sql
appointments (user_id, start_at) INCLUDE (end_at, status)
             WHERE status IN ('pending', 'confirmed')   -- занятость
appointments (user_id, start_at DESC)                   -- календарь и история
appointments (user_id, client_id, start_at DESC)        -- карточка клиента
time_block   (user_id, start_at, end_at)
slot_hold    (master_user_id, expires_at, start_at)
```

Список уточняем по `EXPLAIN` и `pg_stat_statements` на реальных запросах, лишние индексы не держим.

## 5. Кеш и цели по скорости

Кеш добавляем только там, где он нужен. Сначала база рядом с приложением и хорошие запросы,
затем замер и только потом кеш для слотов.

| Данные | Кеш | Сброс |
| --- | --- | --- |
| Username → id мастера | Valkey, 1 ч | при смене username |
| Публичная страница мастера | Valkey, 1 ч + ETag | по версии мастера |
| Расписание и настройки | Valkey, 1 ч | по версии мастера |
| Аналитика | Valkey, 5 мин; закрытые периоды дольше | по версии мастера |
| Занятость и слоты | **сначала без кеша**; после замера, если нужно, свободные интервалы по версии мастера | по версии мастера |
| Проверки при записи, hold, OTP, токены, ссылки клиента | **не кешируем никогда** | — |

**Инвалидация:** у каждого мастера есть счётчик `master:{id}:v`, он входит в ключ кеша.
Action увеличивает его через `DB::afterCommit`, cron-задачи делают то же самое. Старые ключи
истекают сами, искать их по шаблону не нужно. Holds меняются часто, поэтому всегда читаются
из базы.

### Цели

Время на сервере, p95, без учёта сети. Проверяем нагрузочным тестом k6 на staging:

| Запрос | Цель |
| --- | --- |
| `availability`, `nearest` | < 50 мс |
| `hold`, создание брони | < 100 мс |
| Списки в приложении мастера | < 50 мс |
| Аналитика без кеша | < 150 мс |

Сеть до Германии добавит примерно 100–150 мс из Бишкека и Торонто. Это оценка, её проверим
замером в фазе 0. Ускоряют приложение и другие меры:

- подтверждения отправляются через очередь;
- работают HTTP/3 и сжатие;
- остаётся кеш TanStack Query в мобилке.

## 6. Схема БД

Создаём новый чистый baseline на миграциях Laravel. **Имена таблиц и колонок оставляем,
кроме перечисленного ниже**: переименования не ускорят систему, но усложнят перенос и мобилку.

| Изменение | Зачем |
| --- | --- |
| Новая `users`, те же UUID из `auth.users` | все внешние ключи сохраняются |
| Новая `social_accounts` (Google, Apple) | вместо `auth.identities` |
| `personal_access_tokens` с `uuidMorphs` | `users.id` у нас UUID |
| `appointments.end_at` (заполняет триггер), `allow_overlap` | индексируемые интервалы и `EXCLUDE` |
| `appointment_service` со снимком названия, цены, длительности | вместо `service_ids[]`; история не ломается при правке услуги |
| `master_profile.timezone` отдельной колонкой | сейчас часовой пояс лежит внутри JSON |
| Коды OTP: 6 цифр, только хеш, атомарный счётчик попыток | закрывает баг 7 |
| Удаляем `bookings`, `availability`, `create_booking`, `rls_auto_enable` | легаси: обе таблицы пустые |

`schedule` остаётся в JSON, но с валидацией через типизированный объект: дни читаются
только вместе.

## 7. Auth

| Поток | Реализация |
| --- | --- |
| Email-код | `POST /v1/auth/email/send` и `/verify`, лимиты по email и IP, письма через Postmark или Resend, настроенные SPF и DKIM |
| Google | текущий браузерный PKCE-поток: Socialite без сессии, затем одноразовый код в `appmasterseene://`. Нового нативного модуля не нужно |
| Apple | `expo-apple-authentication`, проверка `identityToken` по JWKS. **Нужен новый нативный билд** |
| Сессия | Sanctum: отдельный токен на устройство, 90 дней с продлением, хранится в уже существующем адаптере SecureStore |
| Выход | отзыв токена; отдельно выход со всех устройств |
| Удаление аккаунта | **проверить:** сейчас есть только `deactivated_at`. Правила App Store требуют удаления аккаунта, а для Apple ещё и отзыва токена |

Вход клиента по телефону на сайте остаётся отдельным потоком: OTP и токен устройства
переезжают как есть.

Все пользователи войдут заново один раз, потому что сессии Supabase нельзя перенести. При 4
пользователях это не проблема. Аккаунты сопоставляются по `id`, а новый вход через Apple
привязывается по подтверждённому email.

### Изоляция данных вместо RLS

- Глобальный scope мастера на моделях, Policies на каждую запись, вложенные маршруты со scoping.
- **Обязательный тест на каждый эндпоинт:** мастер A не может прочитать или изменить данные
  мастера B (ожидаем 404). Тест входит в определение готовности эндпоинта.
- `user_id` никогда не берётся из запроса, только из токена.
- Публичные ответы собираются из явного списка полей, чтобы не отдать лишнего.

## 8. Окружения

Решение по хостингу: **VPS с Forge**. Docker Compose для прода не берём: Forge закрывает
деплой, демоны, TLS и обновления с меньшей ручной работой. Провайдер по умолчанию: **Hetzner в
Германии** (Нюрнберг или Фалькенштейн; в самом Франкфурте у Hetzner площадки нет, но задержка
будет близкой). В 2026 у Hetzner были подорожания и нехватка части серверов, так что
наличие и цену проверяем перед заказом. Запасной вариант: DigitalOcean или Vultr во Франкфурте.

| | Local | Staging | Production |
| --- | --- | --- | --- |
| Ветка | любая | `develop` | `main` |
| API | `localhost:8000` | `api.staging.getseene.app` | `api.getseene.app` |
| Сайт | `localhost:3000` | `seene-six.vercel.app` | `getseene.app` (Cloudflare) |
| Серверы | Mac: Herd и Docker | 1 VPS, 2 vCPU / 4 ГБ, всё вместе | app-VPS и DB-VPS, 4 vCPU / 8 ГБ каждый, частная сеть |
| Postgres | Docker | на том же VPS | отдельный VPS с volume |
| Файлы | MinIO | R2 `seene-staging` | R2 `seene-production` |
| Письма | Mailpit | провайдер, только разрешённые адреса | провайдер |
| Сообщения | провайдер `log` | `log` | WhatsApp и Telegram |

### Локально

На этой машине уже есть PHP 8.4, Composer, Herd и Docker.

```bash
composer create-project laravel/laravel apps/api
cd apps/api
php artisan install:api          # Sanctum
composer require laravel/octane laravel/horizon laravel/pulse \
  dedoc/scramble sentry/sentry-laravel laravel/socialite
composer require --dev pestphp/pest larastan/larastan laravel/pint laravel/boost
php artisan octane:install --server=frankenphp
```

- `docker-compose.yml` в корне: `postgres:17`, `valkey`, `mailpit`, `minio`.
- `apps/api/package.json` с обёртками над artisan, чтобы работали `pnpm api test`, а также общие
  `pnpm lint`, `pnpm typecheck` и `pnpm test`.
- `packages/api-contract`: типы, сгенерированные из OpenAPI.
- Для телефона в локальной сети: `php artisan octane:start --host=0.0.0.0` и
  `EXPO_PUBLIC_API_URL=http://<LAN-IP>:8000`.
- Сиды: демо-мастер с услугами и записями, чтобы запускать всё одной командой.

### Сервер и безопасность

- Postgres слушает только частную сеть; наружу открыты только 80 и 443 и только для
  Cloudflare; вход по SSH только с ключом.
- Cloudflare проксирует API; Laravel доверяет его IP и читает `CF-Connecting-IP`.
- Секреты хранятся в окружении Forge, для каждой среды свои.
- Лимиты запросов в Valkey на OTP, `hold`, бронь и `availability`.
- **Проверить в фазе 0:** поддерживает ли штатная настройка Octane в Forge FrankenPHP.
  Если нет, запускаем демоном за Nginx.

### Бэкапы

Supabase закрывал это за нас, а теперь это наша ответственность и главный минус выбранного
хостинга.

- `pgBackRest` с непрерывным архивом WAL в R2: восстановление на момент времени, цель потери
  данных до 5 минут.
- Ночной `pg_dump` к **другому** провайдеру.
- **Проверка восстановления обязательна перед запуском**, затем ежемесячно. Непроверенный бэкап бэкапом не считается.

### CI/CD

`.github/workflows/api.yml` запускается на PR и пушах в `develop` и `main`:

1. Сервисы Postgres 17 и Valkey.
2. Pint, Larastan, Pest (включая изоляцию и перевод часов).
3. Проверка, что OpenAPI и типы в репозитории актуальны.
4. После успеха: deploy hook Forge (`develop` → staging, `main` → production).

Деплой: `composer install --no-dev`, `artisan migrate --force`, `config:cache`, `route:cache`,
`event:cache`, `octane:reload`, `horizon:terminate`. Изменения схемы только обратно совместимые:
сначала добавить, удалить следующим релизом.

### Мониторинг

Sentry для ошибок, Pulse для медленных запросов и очередей, внешний пинг `/up` с оповещением,
алерты на диск, память и возраст последнего бэкапа.

## 9. Фазы бэкенда

Дни рабочие, оценка на одного человека.

| # | Фаза | Дни | Готово, когда |
| --- | --- | --- | --- |
| 0 | Окружения | 3–4 | «hello» отвечает на staging через CI/CD; работают Octane, Horizon, Sentry; бэкап проверен восстановлением; задержка из Бишкека и Канады измерена |
| 1 | Основа и схема | 4–5 | baseline и модели готовы, ETL из staging повторяем, формат ошибок и версионирование заданы, тест изоляции стал шаблоном |
| 2 | Auth | 3–4 | email-код, Google и Apple выдают токен; работают выход и удаление аккаунта |
| 3 | Публичная бронь и слоты | 6–8 | `SlotEngine` покрыт тестами, включая баги 1–6; страница мастера, `availability`, `nearest`, `hold`, бронь, отмена и перенос работают, а гонка из параллельных запросов не даёт двойной брони |
| 4 | API приложения мастера | 5–7 | покрыты 57 функций: записи, клиенты и их слияние, услуги, категории, типы оплаты, личное время, продажи, настройки, онбординг, «внимание» |

В фазе 3 сначала пишем тесты на правила из раздела 4, затем сравниваем старый и новый API на
данных staging. Каждое расхождение должно быть либо багом, либо запланированным исправлением.

`seene-x3z` (провайдер сообщений) подключается в Laravel, когда придёт решение и одобрение Meta.
От этого переход не зависит: до тех пор работает провайдер `log`.

## 10. План перехода

### Принцип

**Параллельный стек с разовым переключением.** Двойной записи в две базы не будет: при таких
объёмах данных это лишняя сложность и источник ошибок. Supabase работает нетронутым, пока
Laravel поднимается рядом со своей базой, а скрипт переноса можно запускать сколько угодно раз.

### Шаги

| # | Шаг | Дни | Что делаем |
| --- | --- | --- | --- |
| 6 | Мобилка | 4–6 | адаптеры в `entities/*/api` за флагом `EXPO_PUBLIC_API_BACKEND=supabase\|laravel`; новая сессия; типы из контракта; новый нативный билд с Apple. Сливается маленькими PR, без долгоживущей ветки |
| 7 | Сайт | 2–3 | `routeRules` proxy по одному маршруту, передача IP клиента, регион Vercel `fra1` |
| 8 | Переключение на staging | 1–2 | по чеклисту ниже |
| 9 | Удаление Supabase и запуск прода | 2–3 | см. ниже |

### Перенос данных

| Откуда | Куда |
| --- | --- |
| `auth.users`, `auth.identities` | `users`, `social_accounts`, с теми же UUID |
| Таблицы `public.*` | 1:1 |
| `appointments.service_ids` | `appointment_service`; снимок берётся из текущих услуг, поэтому **для старых записей он приблизительный** |
| `appointments` | рассчитать `end_at`; `allow_overlap = true` для существующих пересечений |
| `booking_link`, `client_device_token`, `phone_verification` | 1:1: ссылки и доверенные устройства продолжат работать, если перенести `phoneVerificationTokenSecret` и алгоритм хеширования |
| `otp_codes`, `slot_hold` | не переносим, это короткоживущие данные |
| `bookings`, `availability` | не переносим, обе таблицы пустые |
| Storage | `rclone` в R2, затем замена URL в `avatar_url` и других полях с адресами файлов |

Проверка после каждого запуска: количество строк, сумма `sale.amount` по мастеру, отсутствие
«висячих» внешних ключей и совпадение слотов на контрольных датах.

### Чеклист переключения

- [ ] Все фазы приняты, `k6` укладывается в цели, тесты изоляции зелёные.
- [ ] Предупредить тестировщиков и не менять данные в старом приложении.
- [ ] Финальный ETL и сверка.
- [ ] Включить новый backend на сайте, опубликовать мобильный билд с флагом `laravel`.
- [ ] Пройти сценарий: вход всеми способами → онбординг → услуга → бронь с сайта → отмена и
      перенос по ссылке → запись мастера → продажа → аналитика.
- [ ] Отслеживать Sentry и Pulse 48 часов.

**Откат:** вернуть флаги на Supabase, он остаётся нетронутым. Данные, созданные после
переключения, потеряются; на staging это приемлемо.

### Удаление и прод (шаг 9)

1. Через 2 недели стабильной работы удалить флаги, адаптеры, `@supabase/supabase-js` и `database.types.ts`.
2. Перенести `supabase/migrations` в архив. Обновить `AGENTS.md` (новые правила БД: теперь есть локальная база),
   `apps/web/CLAUDE.md` и `apps/mobile/docs/*`.
3. Поднять прод: Forge, Postgres, бэкапы с проверкой восстановления, Cloudflare для сайта и API.
   Разделы «прод на Cloudflare» и «первый релиз в сторы» из текущих планов идут уже на новой основе.
4. Сделать финальный `pg_dump`, сохранить отдельно, поставить проект Supabase на паузу, а удалить только через месяц.

### Заморозка на время перехода

- Новые миграции в `supabase/` не добавляем.
- Новая работа со схемой и серверной логикой делается сразу в Laravel.
- Чистый UI в мобилке и на сайте продолжается.
- Текущие PR, уже идущие на Supabase, сливаем **до** первого ETL или переносим в Laravel.

## 11. Что мы теряем и риски

| Риск | Что с ним делаем |
| --- | --- |
| Ошибка в изоляции мастеров: утечка данных | обязательный тест на эндпоинт; tenant scope; ревью |
| Потеря данных на своём Postgres | pgBackRest, второй бэкап у другого провайдера, проверка восстановления |
| Весь сервер и база на нас: сбои, обновления, диск | алерты; в проде база отдельно; плановые обновления; нет failover на старте, простой при сбое железа до восстановления |
| Утечка состояния между запросами в Octane | никакого состояния запроса в singleton; тесты; `max-requests` |
| Студия Supabase пропадает | TablePlus через SSH; при необходимости позже Filament |
| Письма: теперь доставляемость на нас | отдельный поддомен, SPF, DKIM, DMARC |
| Персональные данные клиентов из Канады в Германии | **проверить с юристом** до запуска в Канаде, особенно Квебек |
| Перенос затянется и застопорит продукт | заморозка только схемы; фазы с понятным результатом; UI продолжается |
| Требования App Store | Apple и удаление аккаунта входят в фазу 2; перед отправкой сверить с актуальными правилами |

Стоимость: появятся счета за серверы, Forge, письма и R2, а счёт за Supabase исчезнет. Точные
цифры надо собрать перед заказом: цены Hetzner в 2026 менялись, а данные по Forge у меня только
из сторонних источников (примерно от $12 в месяц за аккаунт).

## 12. Открытые вопросы

Не блокируют старт, закрываем по ходу.

1. Может ли мастер сознательно создать запись поверх другой (фаза 1)?
2. Какой выбрать провайдер писем: Postmark или Resend (фаза 0)?
3. Нужен ли failover базы к запуску? Предложение: нет, вернёмся после первых платящих мастеров.
4. Какой срок токена устраивает: 90 дней с продлением, или короче?
