# Navigation Architecture

> Version 1.1 · 2026-08-26 · [Architecture](./)

## Overview

Seene uses Expo Router as its only router. Files under `src/app/` define the navigation hierarchy;
`_layout.tsx` files configure navigators; routes compose screen-level widgets and features. There is
no custom router, duplicated navigation store, or mount-time redirect wrapper.

This architecture is implemented for Expo SDK 57 (`expo-router ~57.0.16`, React Native 0.86.2).
Native Tabs are an **alpha** Expo Router API in this version, so their import is isolated in one
layout. Protected routes and native Stack presentation are stable APIs. Typed routes are enabled in
`app.json` and are generated by Expo CLI.

## Architecture

### Route tree

```text
src/app/
├── _layout.tsx                         root providers + protected route branches
├── session-restoring.tsx               session/profile restoration state
├── session-error.tsx                   retryable restoration failure
├── +not-found.tsx
├── (auth)/                             public while signed out
│   ├── _layout.tsx                     auth Stack
│   ├── sign-in/index.tsx               /sign-in
│   ├── sign-in/email.tsx               /sign-in/email
│   └── email.tsx                       legacy /email redirect
├── (onboarding)/                       signed in, profile not yet created
│   ├── _layout.tsx
│   ├── onboarding.tsx                  /onboarding
│   └── welcome.tsx                     legacy /welcome redirect
├── (app)/                              signed in with an active profile
│   ├── _layout.tsx                     tabs base + pushed screens + sibling modals
│   ├── analytics.tsx                   /analytics, pushed from "Сегодня"
│   ├── clients/[clientId].tsx          /clients/[clientId], pushed over the tab bar
│   ├── settings/profile.tsx            /settings/profile, pushed over the tab bar
│   ├── settings/services.tsx           /settings/services, pushed over the tab bar
│   ├── (tabs)/
│   │   ├── _layout.tsx                 the only NativeTabs integration point
│   │   ├── (home)/_layout.tsx          nested Stack; canonical / entry
│   │   ├── (calendar)/_layout.tsx      nested Stack; /calendar
│   │   ├── (clients)/_layout.tsx       nested Stack; /clients
│   │   └── (settings)/_layout.tsx      nested Stack; /settings
│   └── (modals)/
│       ├── appointment-form.tsx           standard route modal
│       ├── checkout/[appointmentId].tsx   native form sheet
│       └── quick-create/                   fullscreen modal with nested Stack
│           ├── _layout.tsx
│           ├── index.tsx
│           ├── client.tsx
│           ├── services.tsx
│           ├── date-time.tsx
│           └── review.tsx
└── (dev)/                             compiled route, accessible only in development
    └── uikit/                         catalog and executable navigation examples
```

Route groups organize navigators without changing public URLs. Production links should normally use
canonical absolute paths such as `/clients/[clientId]`. Use a group-qualified path only when the
origin navigator matters, as it does for the appointment route shared by Home and Calendar.

### Navigator responsibilities

| Tool                 | Current responsibility                                                                              | Add it when                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Root `Stack`         | Providers and mutually exclusive session branches                                                   | Always; it is the app shell                                        |
| `Stack.Protected`    | Makes auth, onboarding, app, restoration, and dev routes available only while their guards are true | Access depends on session/application state                        |
| Application `Stack`  | Keeps Native Tabs as the base; pushed screens and route modals are siblings above it                | A screen pushed from a tab, or presented above the whole tab bar   |
| Nested tab `Stack`   | The tab root's native header (large title, toolbar, search)                                         | A tab root needs native header configuration                       |
| `NativeTabs`         | Four primary destinations; the floating "+" create card sits over the bar                          | A destination is a peer users switch between frequently            |
| Shared route group   | One appointment detail implementation in Home and Calendar stacks                                   | The same screen must retain the navigator context that opened it   |
| Route modal          | Deep-linkable editing, checkout, and multi-step creation                                            | The overlay is navigation state or owns multiple screens           |
| `Modal` / `Sheet` UI | Blocking confirmation or transient picker/preview                                                   | The overlay is local UI state and is not a navigable workflow      |

Detail screens are not routes of a tab's Stack: a screen pushed there would sit under the tab bar.
They are routes of the application Stack, so the push slides over the bar and Back reveals it
again — the native "hides bottom bar when pushed" behaviour.

There is no Drawer. The current information architecture already has four primary tab destinations
and no secondary global destination set that warrants another persistent navigator. Add a Drawer
only after a product scenario defines what it owns; do not add one as a capability demo.

### Protected routing and authentication

`src/app/_layout.tsx` keeps a single root navigator mounted and derives five states from the session
store:

```text
restoring session/profile       → session-restoring
restoration failed              → session-error
no session                      → (auth)
session, no master profile      → (onboarding)
session + active profile        → (app)
```

`Stack.Protected` removes unavailable screens from navigation history when a guard changes. Signing
out therefore exposes `(auth)` and prevents native Back from reopening protected screens; the
application does not push a sign-in route manually. This is client navigation protection only —
Supabase RLS remains the authorization boundary for data.

The session store subscribes to `onAuthStateChange` before restoring the current session. Its auth
callback stays synchronous and defers profile loading outside Supabase's auth lock. Concurrent
profile reads are deduplicated, stale responses are ignored, and restoration errors expose an
explicit retry route.

### Deep-link return flow

`useAuthReturnIntent` records only the incoming external deep link while protected routing is not
available. `sanitizeReturnTo` accepts local absolute paths, rejects external or public/auth paths,
and never mirrors navigation state into a store. After authentication and, when required,
onboarding, the root layout performs one `router.replace(returnTo)` and clears the transient intent.

No authentication rewrite hook is installed. The current first-party email flow and custom scheme
do not need a provider callback rewrite. If a future OAuth provider supplies non-canonical callback
URLs, normalize those URLs at Expo Router's system-path boundary; do not add redirect effects to
screen wrappers.

### End-to-end flow

```text
protected launch or deep link
  → restore session/profile
  → signed out: /sign-in
  → authenticated without profile: /onboarding
  → profile ready: original protected route, otherwise /
  → switch Native Tabs
  → open shared /appointments/:id in the current tab Stack
  → present /quick-create above all tabs
  → push client → services → date-time → review inside modal Stack
  → Back pops one modal step; close dismisses to the origin
  → finish uses dismissTo('/') to close the complete flow
  → sign out; protected history is removed; /sign-in becomes available
```

Native Stack owns headers, swipe gestures, transition animations, iOS modal behavior, and normal
Android Back. Intercept Android Back only for local state that should pop before navigation (the
onboarding wizard does this for earlier steps) or for an explicit unsaved-change decision. The
shared `Sheet` intercepts Android Back only while it is open and dismisses itself.

### Theme-aware native headers

Regular page Stacks and route-modal Stacks keep Expo Router's native header and provide
`NavigationHeaderBackground` through `headerBackground`. The component renders only the visual
`LinearGradient`; it does not wrap a screen or hide navigator options. Its start/end colors come
from the active Unistyles semantic roles
`colors.navigation.headerGradientStart|headerGradientEnd`. Header tint, status-bar contrast,
shadow visibility, and transparency remain explicit in the owning `_layout.tsx`.

Route layouts import this component from its focused entry point
`@/shared/ui/NavigationHeaderBackground`. Expo's web static route manifest evaluates layout modules
before the app bootstrap has selected a Unistyles theme; importing the complete `@/shared/ui` barrel
there would eagerly evaluate unrelated theme-dependent stylesheets. Normal screens continue to use
the UIKit barrel.

The header is transparent on iOS, where scroll wrappers use automatic native content insets. On
Android it remains in normal layout flow so static content and form fields are not obscured by an
absolute header. This platform difference does not change Back, gestures, presentation, or the
gradient itself. The native form sheet remains the deliberate exception: its header is hidden and
`FormSheetContent` renders cross-platform title/actions because Android form-sheet header behavior
differs from iOS.

### Modal decisions

| Pattern              | Configuration                                               | Use                                                     |
| -------------------- | ----------------------------------------------------------- | ------------------------------------------------------- |
| Standard modal       | `presentation: 'modal'`                                     | Focused create/edit screen that returns to its origin   |
| Fullscreen modal     | `presentation: 'fullScreenModal'` + nested Stack            | Long, focused, multi-step workflow such as quick create |
| Form sheet           | `presentation: 'formSheet'`, numeric detents `[0.45, 0.85]` | Compact checkout flow                                   |
| React Native `Modal` | Local `visible` state                                       | Blocking confirmation only                              |
| Gorhom `Sheet`       | Ref-controlled transient overlay                            | Preview, picker, or action sheet without route identity |

The form sheet renders its title/actions inside `FormSheetContent`, because Android form sheets do
not provide the same native Stack-header behavior as iOS. Numeric detents are deliberately limited
to two; Expo Router 57's Android integration should use no more than three. Navigation presentation,
gestures, and detents remain in the parent `_layout.tsx`, never in visual wrappers.

## Configuration

- `app.json → expo.scheme`: `appmasterseene` enables native deep links.
- `app.json → expo.experiments.typedRoutes`: `true` enables generated typed `Href` validation.
- `app.json → expo.web.output`: `static`; native-only storage has `.web.ts` adapters so route
  generation and static rendering do not load SecureStore/MMKV.
- `src/app/(app)/(tabs)/_layout.tsx`: contains the only alpha Native Tabs import. Do not add a
  custom background; iOS owns the native tab-bar material.
- Regular nested Stacks configure `NavigationHeaderBackground`, theme-aware header tint and
  status-bar contrast explicitly. Do not move those options into a screen wrapper.
- Every nested Stack exports `unstable_settings.initialRouteName` so deep links have a predictable
  initial screen and a valid Back destination.

## Visual screen wrappers

Wrappers own visual/system content environment only. They do not call `router`, install route
guards, set Stack presentation, or hide navigation options.

| Wrapper            | Responsibility                                                                          | Deliberate props                                                          | Do not put here                               |
| ------------------ | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | --------------------------------------------- |
| `Screen`           | Static canvas, selected safe-area edges, optional padding/centering                     | `padded`, `center`, `edges`, `style`, `contentStyle`                      | Header, gestures, route redirects, scroll     |
| `ScreenScrollView` | Canvas, native scroll insets, padding, tap/indicator policy                             | Normal `ScrollViewProps`, `padded`, `contentContainerStyle`               | Stack options, keyboard form footer           |
| `FormScreen`       | Keyboard avoidance, scrollable fields, fixed reachable footer, selected safe-area edges | `footer`, `padded`, `edges`, `contentContainerStyle`, normal scroll props | Presentation, close/back logic, unsaved guard |
| `FormSheetContent` | Cross-platform content title/actions for a native form sheet                            | `title`, `description`, `headerLeft`, `headerRight`, `footer`             | Detents, presentation, gestures               |

No generic `PageLayout`, `ModalLayout`, or `ScreenHeader` exists. Those abstractions mixed visual
layout with navigator configuration and duplicated native Stack behavior. `Footer` and
`ScrollFade` remain standalone visual primitives for screens that demonstrably need them. A
fullscreen modal uses the same `FormScreen`; presentation mode is not a reason to duplicate a
wrapper.

The root `StatusBar` follows the active Unistyles theme, including a manually forced theme. A Stack
screen option overrides it when a route background needs different contrast; the photo sign-in
route is the current example. Loading and error states are explicit routes/components, not wrapper
side effects.

## Usage

### Add a static screen to an existing tab

Create the route under that tab's group and register its native title in the tab `_layout.tsx`:

```tsx
export default function ExampleScreen() {
  return <Screen edges={['left', 'right']}>{/* content */}</Screen>;
}
```

The Stack owns the native header. On iOS, scroll wrappers request automatic native insets under the
transparent gradient header. Static content that intentionally excludes the top safe-area edge
must either tolerate the header overlay or override `headerTransparent: false`; the wrapper still
owns only its declared safe-area edges.

### Add a dynamic route

Use a serializable identifier and a typed object href:

```tsx
router.push({
  pathname: '/clients/[clientId]',
  params: { clientId },
});
```

Read it with `useLocalSearchParams<{ clientId: string }>()`. Do not store the selected entity in a
global navigation store.

### Open a shared appointment route

Use the origin group's qualified path when retaining the selected tab is required:

```tsx
router.push({
  pathname: '/(app)/(tabs)/(calendar)/appointments/[appointmentId]',
  params: { appointmentId, source: 'calendar' },
});
```

### Add a modal flow

Place it under `(app)/(modals)`, configure its `presentation` in `(app)/_layout.tsx`, and add a
nested `_layout.tsx` only if the flow really contains multiple routes. Within the flow, use normal
`router.push`/native Back. Use `router.dismiss()` to return to the exact origin or
`router.dismissTo('/')` only for a defined terminal destination.

### Choose declarative or imperative navigation

- Prefer `Link` for visible destinations and deep-linkable actions.
- Use `router.push` after an event or when params are assembled programmatically.
- Use `router.replace` only when the previous location must not remain in history (validated auth
  return is the current example).
- Use `router.back`/native Back for Stack history; avoid hard-coded destination pushes as a Back
  substitute.
- Use `router.dismiss` and `dismissTo` only for presented modal history.

## UIKit catalog

`/uikit` is an executable, development-only catalog. The root guard is
`<Stack.Protected guard={__DEV__ && canUseApp}>`; production users cannot enter it even through a
deep link. Its sections cover foundations, components, page layouts, navigation, modals, and
authentication. Example cards include intent, recommendation, source path, a small code fragment,
and a working route/action when one is meaningful.

Production routes provide the real Stack, Native Tabs, shared route, and modal examples. The catalog
does not create a parallel demo navigator or modify production navigation state beyond the action a
developer explicitly opens.

## Verification

Run these after any route-tree change:

```sh
bunx tsc --noEmit
bunx expo lint
bun run test -- --runInBand
bunx expo export --platform web --output-dir <temporary-directory>
```

For native behavior, verify a development build on both platforms: selected-tab retention, native
header Back, Android hardware Back, iOS swipe-to-go-back, modal dismiss, form-sheet detents, cold
deep-link restoration, and sign-out history removal. Native Tabs remain alpha, and Liquid Glass
requires a binary built with the iOS 26 SDK; treat SDK upgrades as a focused compatibility review.
